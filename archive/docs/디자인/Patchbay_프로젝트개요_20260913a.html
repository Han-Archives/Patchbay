Patchbay · Project Overview

프로젝트를 잭과 와이어로 다루는 스튜디오 커널

Patchbay는 여러 프로젝트를 오가며 일할 때 흩어지는 것들 — 스킬, 규칙, 진행 상황, 미완의 연결 — 을 물리적인 패치베이처럼 한곳에서 조망하고 이어주는 로컬 커널이다. Cursor·Claude Code·터미널·(신규) 텔레그램, 어떤 호스트에서 접근하든 같은 온톨로지와 같은 파일을 본다.

Draft · 구현 착수 전 (Phase 0 시작 전)

01 — 왜 만드는가

문제: 프로젝트마다 컨텍스트가 따로 논다

여러 레포를 오가다 보면 어떤 프로젝트에 어떤 스킬을 심어뒀는지, 어떤 규칙을 정했는지, 지금 뭘 하다 멈췄는지가 각 레포 안에 흩어진다. 포트폴리오 전체를 한눈에 보는 곳이 없고, "이 스킬을 저 프로젝트에도 연결했던가"를 매번 다시 확인해야 한다.

Patchbay는 이 상태를 오디오 패치베이의 언어로 옮긴다. 프로젝트의 스킬·소스·산출물은 잭(Jack)이고, 스킬을 프로젝트에 심는 행위는 패치(Patch)이며, 실제로 코드에서 그 연결이 쓰이고 있다는 증거가 발견되면 와이어(Wire)가 된다. 심었지만 안 쓰이는 패치, 심지 않았는데 발견되는 와이어 — 이 어긋남 자체가 신호다.

02 — 어떻게 동작하는가

호스트는 여럿, 커널은 하나

Cursor·Claude Code·터미널·텔레그램은 모두 호스트다. 호스트마다 다른 LLM, 다른 화면을 쓰지만, 프로젝트 상태를 읽고 쓰는 통로는 하나로 좁힌다 — MCP 아니면 CLI, 그리고 그 둘은 반드시 Core를 거친다. Core 자신은 LLM을 부르지 않는다. 결정은 항상 호스트 쪽 LLM이 내리고, Core는 결정적인 파일 I/O만 한다.

"MCP와 CLI는 반드시 Core를 거친다."

이 규칙은 세션이 여러 개로 늘어나도 그대로다. 한 프로젝트를 여러 LLM 세션이 나눠 맡는 멀티 에이전트 역할 분담(신규, Phase 12)도 Patchbay가 세션 사이를 직접 잇지 않는다 — 리더 세션이 역할을 assignments.yaml에 쓰면, 워커 세션이 그 파일을 읽고 작업한 뒤 산출물을 다시 파일로 남긴다. 자동 호출도, 폴링도, 알림도 없다. 오케스트레이션 엔진이 아니라 공유 파일을 통한 비동기 협업이다.

03 — 지키는 것과 안 하는 것

Patchbay가 아닌 것

다섯 가지 금지선

  • 호스트를 대체하는 새 UI가 아니다 — Cursor·Claude Code·터미널·텔레그램을 그대로 쓴다
  • 커널이 LLM을 부르지 않는다 — 결정은 항상 호스트 쪽 LLM이 내린다
  • SQLite나 클라우드 DB를 기본값으로 깔지 않는다 — 상태는 사람이 읽는 마크다운·YAML 파일이다
  • n8n류 실행 그래프 도구가 아니다 — 자동 실행을 오케스트레이션하지 않는다
  • 상시 워치·서버가 몰래 켜지지 않는다 — 텔레그램 호스트조차 수동 기동만 허용한다

실제로는 이보다 세밀한 14개 원칙 자가 점검 목록을 구현 내내 열어두고 확인한다 (명세 2절). 그중 자주 걸리는 것들:

07라벨 없는 잭이 방치되고 있지는 않은가
08Patch와 Wire를 같은 것으로 취급하고 있지는 않은가
09L1이 L2 텍스트를 잘라 만든 것은 아닌가
13생성 파일을 지키려 스캔을 건너뛰고 있지는 않은가
14텔레그램이 읽기 이외의 툴을 노출하고 있지는 않은가

04 — 프로젝트를 스튜디오에 들이는 법

세 가지 온보딩 시나리오

지금 상태가 빈 캔버스인지, 정리된 기존 코드인지, 엉망진창인지에 따라 진입 경로가 다르다. 정리(C)는 종착점이 아니다 — 정리를 마치면 반드시 A나 B로 합류한다.

A

new-project

빈 캔버스. 대화형 설계 인터뷰로 처음부터 정의한다.

B

adopt-project

정리된 기존 코드. 발굴 후 사용자 확인을 거쳐 이어받는다.

C

triage-project

엉망진창. 클러스터 가설을 제시하고 _archive/·_needs-review/로만 정리한 뒤 A/B로 보낸다.

flowchart LR
  Start[프로젝트를 스튜디오에 들인다]
  Start --> QA{지금 상태는}
  QA -->|빈 캔버스| A[A. new-project]
  QA -->|정리된 기존 코드| B[B. adopt-project]
  QA -->|엉망진창| C[C. triage-project]
  C --> Choice{정리 후 사용자가 선택}
  Choice -->|처음부터 설계| A
  Choice -->|발견된 의도 이어가기| B
  A --> Common[공통 루프: scan to propose to patch]
  B --> Common
