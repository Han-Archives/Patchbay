## 0. 검토자에게 바라는 것

1. 포지션이 Dify/n8n/Cursor/Claude Code와 실제로 겹치지 않는가.
2. “호스트 LLM이 제안을 쓰고, 커널은 스캔만 한다”가 솔로 빌더 루프에서 마찰을 키우지 않는가.
3. 온톨로지 v0이 너무 크거나, 빠진 클래스가 있는가.
4. 파일이 소스 오브 트루스인 설계가 git·멀티 프로젝트에서 깨지는 지점은 어디인가.
5. v1 범위가 아직도 넓은가. 무엇을 더 잘라야 첫 유용한 슬라이스가 되는가.
6. TypeScript + CLI + MCP + 선택 XYFlow 스택이 이 제품에 맞는가.
7. 레이어 경계(L1/L2/L3)가 결정적으로 유지될 수 있는가.
8. 파일 기반 진행 대시보드가 "실시간" 기대를 충분히 충족하는가.
9. (c판) 온보딩 스킬 3종(`new-project`/`adopt-project`/`triage-project`)이 실제로 서로 겹치지 않는 경계를 가지는가. 특히 `triage-project`가 나머지 둘로 "합류"하는 설계가 실제로 깔끔한가, 아니면 억지 결합인가.

동의하지 않으면 대안을 **대체 설계**로 적어 달라.

## 1. 한 줄 정의

**Patchbay는 여러 LLM 프로젝트를 하나의 스튜디오로 보이게 만드는 로컬 패치 패널이다.**

오디오 패치베이 은유: 랙=프로젝트, 잭=스킬/소스/모델/산출물/시그널, 라벨 스트립=온톨로지, 케이블=Patch(의도)/Wire(실제), 미터=대시보드 가이드.

이름에 대한 참고: 표면 이름 중 **Atlas**만 오디오 은유가 아니라 별도 은유(지도책)를 쓴다. 라벨 스트립(온톨로지)이 실제로 렌더링된 화면이 Atlas라는 점에서 기능적으로는 이어지지만, 이름 계열은 의도적으로 예외로 남겨둔다 (결정 로그 참고).

## 2. 문제

(20260912b와 동일 — 변경 없음)

솔로 빌더가 LLM 프로젝트를 여러 개 굴릴 때 막히는 지점은 “실행 엔진이 없다”가 아니라 **조각이 한눈에 안 보인다**는 것. 차별점은 오케스트레이션이 아니라 **조망 + 의미 + 제안**.

---

## 3. 제품 원칙

1. **호스트를 대체하지 않는다.**
2. **커널은 결정적이다.**
3. **제안은 호스트 모델이 한다.**
4. **파일이 소스 오브 트루스다.**
5. **세 면에 같은 모델.**
6. **실행 그래프는 수입할 수 있지만 핵심이 아니다.**
7. **이름 없는 잭은 부채다.**
8. **Patch와 Wire를 구분한다.**
9. **정보는 레이어로 나뉜다.** 최소 3단계 상세도(L1 요약/L2 개요/L3 상세), 레이어는 압축이 아니라 결정적 집계 함수의 출력.
10. **진행 상태도 파일이다.** 상시 워치 없이 에이전트가 스텝마다 상태 파일을 갱신.
11. **(c판) 삭제 대신 보관한다.** 정리(triage) 과정에서 폐기 후보로 판단된 파일도 삭제하지 않고 `_archive/`로 이동한다. 확신이 낮은 판단은 스킬이 대신 내리지 않고 사람에게 미룬다(`_needs-review/`).

## 6. 사용자 루프 (c판 재구성 — 세 온보딩 시나리오로 분리)

### 6.0 진입 경로 선택

프로젝트를 스튜디오에 들이는 방법은 상태에 따라 셋으로 갈라진다.

| | A. 신규 생성 | B. 기존 이식 | C. 정리되지 않은 프로젝트 |
|---|---|---|---|
| 전제 상태 | 빈 캔버스 | 코드+이력 있고 서사가 살아있음 | 서사가 없거나 깨짐, 여러 아이디어 혼재 가능 |
| 진입 CLI | `project new` | `project add` | `project triage` (또는 `add`가 자동 전환 제안) |
| 스킬 | `new-project` | `adopt-project` | `triage-project` |
| 사용자가 답하는 것 | 설계 질문(미래) | 확인 질문(현재 상태가 맞나) | 분류 질문(이게 뭐였나, 살았나 죽었나) |
| 종착점 | 그 자체로 완결, 6.4로 진입 | 그 자체로 완결, 6.4로 진입 | **A 또는 B로 합류** (독립 종착점 아님) |

### 6.1 신규 프로젝트 (`new-project`)

1. 트리거: "새 프로젝트 시작하자" 또는 `patchbay project new <alias>`.
2. `new-project` 스킬이 대화형 인터뷰: 한 줄 정의, 문제, 1차 사용자, 쓸 면, 비범위, 성공 조건. "빠른 시작"은 1번·6번만 묻고 나머지는 기본값.
3. `docs/<alias>_기획_YYYYMMDDa.md` + `ROADMAP.md`를 **프로젝트 레포 안에** 생성 (Patchbay 자기 문서와 동일 컨벤션).
4. CLAUDE.md/AGENTS.md/.cursor/rules 새로 스캐폴딩, 기획서를 소스 오브 트루스로 참조.
5. Skill Bay에서 추천 스킬 선택·패치.
6. 사용자가 diff로 승인 → 6.4로 진입.

### 6.2 기존 프로젝트 이식 (`adopt-project`)

1. 트리거: `patchbay project add <path> --alias <alias>`.
2. 커널이 git/README/CLAUDE.md 등 결정적 스캔.
3. `adopt-project`가 문서·커밋에서 기획 의도를 L1/L2로 발굴해 제시 → 사용자가 맞다/틀리다로 정정 (새로 쓰지 않고 발굴+검증).
4. 커밋 패턴 기반 진행 상태 추정 → 사용자 확인 후에만 `progress.yaml.current`에 기록.
5. 기존 계획이 있으면 확인, 없으면 짧게 물어 `ROADMAP.md` 역산 생성.
6. 기존 CLAUDE.md/.cursor/rules는 덮어쓰지 않고 diff로 보강만 제안.
7. 승인 → 6.4로 진입.

### 6.3 정리되지 않은 프로젝트 (`triage-project`)

1. 트리거: `patchbay project triage <path>`, 또는 `project add`가 clarity score(열린 질문 9 참고) 낮은 폴더를 만나 전환 제안.
2. 커널이 **포렌식 스캔**(LLM 없음): git 품질, README 신뢰도, 파일 트리, 중복/유사 파일명(`_v2`, `_final`, `_backup`), 최근 수정일 분포, 고아 파일, TODO/FIXME 밀도 → `excavation.json`.
3. `triage-project`가 클러스터 가설을 카드로 제시("이 폴더에 프로젝트가 N개 섞인 것 같다") → 사용자가 분리/병합/보존/폐기 후보로 표시.
4. 확신도 낮은 파일만 배치 질문으로 확인 → "모르겠음"은 `_needs-review/`로 보류.
5. diff 승인 → 폐기 후보는 삭제 대신 `_archive/YYYYMMDD/`로 이동(원칙 11), 살아있는 코드는 클러스터별 재배치.
6. 사용자가 **명시적으로 선택**: (a) 처음부터 설계 다시 잡기 → 6.1로 진입(정리된 클러스터가 인터뷰 기본값을 채움), 또는 (b) 발견된 의도 이어가기 → 6.2로 진입(정리된 클러스터가 발굴 입력 자료).

### 6.4 공통 루프 (등록 이후, 세 경로 합류 지점)

1. `patchbay project add`(내부적으로 확정) → 최초 `scan` → `inferred.json`/`ATLAS.md`/`ATLAS.digest.md`/`FLOW.md` 생성. `progress.yaml`에 최초 history 기록.
2. Cursor/Claude Code에서 `propose-ontology`/`propose-dashboard` 실행, 진행 중 `PROGRESS.md` 갱신.
3. 초안이 `ontology/`, `DASHBOARD.md`, `overlay.yaml`에 쓰임. 사용자가 diff로 남기거나 되돌림.
4. Skill Bay에서 공용 스킬 패치.
5. 다음 `scan`이 맵을 갱신. `patchbay atlas --level 1`/`patchbay progress`로 요약 확인.

## 9. 로컬 스튜디오 파일 형식

(20260912b 트리에 아래 추가)

### 9.6 프로젝트 자체 문서 vs 스튜디오 메타 문서 (c판 신설)

두 종류를 섞지 않는다.

- **프로젝트 자체 문서** — `docs/<alias>_기획_YYYYMMDDa.md`, `ROADMAP.md`. **대상 프로젝트 레포 안**에 위치, git 이력과 함께 산다. `new-project`/`adopt-project`가 씀.
- **스튜디오 메타 문서** — `ATLAS.md`, `FLOW.md`, `PROGRESS.md`, `DASHBOARD.md` 등. **studio 홈**(`<studio>/projects/<alias>/`)에 위치, Patchbay의 관측 결과.

### 9.7 triage 산출물 (c판 신설)

프로젝트 레포 안에 생성(대상 레포의 실제 구조 변경이므로):

```
<project>/
  _archive/<YYYYMMDD>/      # 폐기 후보, 삭제 아님
  _needs-review/            # 확신 낮은 파일 보류
```

`excavation.json`은 포렌식 스캔 원본으로 studio 쪽 `inferred.json`과 별개 취급(스캔 방식이 다름 — 표준 스캔이 아니라 포렌식 스캔).

## 10. 내장 스킬 초안 (c판 확장)

기존 3종(`map-project`, `propose-ontology`, `propose-dashboard`)은 20260912b와 동일. 아래 3종 추가.

### `new-project` (신설)

빈 프로젝트에 대해 대화형 설계 인터뷰를 진행하고 `docs/<alias>_기획_*.md` + `ROADMAP.md` + CLAUDE.md/rules 초안을 쓴다. "빠른 시작" 모드 지원. `progress.yaml`에 시작/종료를 기록.

### `adopt-project` (신설)

기존 문서·커밋에서 기획 의도와 진행 상태를 **발굴 후 사용자 확인**을 받아 기록한다. 기존 CLAUDE.md/rules는 덮어쓰지 않고 diff로만 보강. 확인 전 `progress.yaml.current`에 추정값을 쓰지 않는다.

### `triage-project` (신설)

포렌식 스캔(`excavation.json`) 결과로 클러스터 가설을 제시하고, 사용자 확인을 받아 분리/병합/아카이브 diff를 만든다. 삭제하지 않는다(원칙 11). 완료 후 반드시 `new-project` 또는 `adopt-project`로 사용자를 안내한다 — 독립 종착점이 아니다.
