# Neo4j 지식 그래프 재설계 — Claude 검토 요청본

작성일: 2026-10-16. 상태: 조사에 근거한 제안, 구현·채택 전.

## 사용자 요청과 조사 범위

Patchbay 왼쪽 아래 지식 그래프를 한빛 강의 https://www.hanbit.co.kr/product/C8863315103 의 주요 내용을 적용하는 방향으로 재설계한다. 먼저 자료와 현재 코드를 조사하고 계획을 세운 뒤 Claude 검토를 받고, 그 검토를 반영하여 산출물 안 네 가지를 제안한다.

링크는 책이 아니라 영상 강의다. 공개 목차만 확인했으며 유료 영상·실습 코드는 보지 않았다. 목차에는 속성 그래프, Cypher, GDS 중심성·커뮤니티·유사도·경로, GraphQL, APOC/CSV/JSON, Bloom, PROFILE/INDEX, Python, 비정형 문서의 지식 그래프 구축, GraphRAG가 있다. 아래 계획은 이 주제를 공식 자료와 현재 코드에 연결한 설계자의 제안이다.

우선 가정: 프로젝트 문서·대화의 본문에서 개념·대상·관계를 만들고 출처를 따라가며 질문하는 기능이 중심이다. 요구사항·코드·시험 연결은 기존 구조를 재사용하는 보조 맥락이다. 사용자가 범위를 답하면 달라질 수 있다. 모든 프로젝트 전체를 즉시 수집하지 않는다.

## 현재 코드에서 확인한 차이

- KnowledgePane.tsx / neo4jContract.ts: File, Folder, Skill, Artifact, Requirement, Eval, AgentNode, Document, Run 등을 표시한다. 파일 스캔뿐 아니라 승인된 설계와 실행 관계도 있다.
- knowledgeView.ts: 스캔/설계/실행 복제 스냅샷을 Neo4j에 넣고 조회한다. 별도 문서 호출은 메모리에서 키워드와 1~2홉을 계산한다.
- neo4jAdapter.ts: 이름·경로·본문 일부의 문자열 CONTAINS 검색과 이웃 조회. replaceAlias는 해당 alias의 :Knowledge 노드를 DETACH DELETE한 후 스냅샷을 재생성한다. 이 영역에 사람의 의미 지식을 섞으면 스캔 시 소실될 수 있다.
- 문서 본문→분할→개체/관계 후보 추출→동일 개체 판별→근거 검토→승인된 의미 그래프의 파이프라인은 현재 지식 그래프 기능에 없다. 다른 부분에 설계 IR은 있으므로 제품 전체에 의미 모델이 없다는 뜻은 아니다.
- app/docker-compose.yml은 neo4j:5.26-community를 선언한다. GDS/APOC 설정은 없다. 실제 실행 DB 버전과 설치 플러그인은 이번 조사에서 확인하지 않았다.

## 먼저 답할 질문

화면 배치보다 아래 질문과 기대 정답·근거를 먼저 작성한다.

1. 이 프로젝트에서 사용하는 핵심 개념은 무엇이며 어느 문단에서 설명하는가?
2. 같은 대상을 다른 이름으로 부르는 자료가 있는가?
3. A와 B는 어떤 관계로 연결되며 그 연결마다 원문 근거가 있는가?
4. 문서 수정으로 어떤 기존 주장과 답변의 근거가 낡았는가?
5. 두 자료가 같은 주제에 대해 서로 다른 내용을 주장하는가?
6. 질문에 대한 답이 없을 때, 부족한 근거를 구별해 보여주는가?
7. 승인된 관계에서 함께 묶이는 주제·연결 중심 개념은 무엇인가? 분석 결과가 참/중요도 보증으로 오해되지 않는가?

## 공통 데이터 설계

문서 구조와 내용의 의미를 함께 보존한다.

Document → HAS_VERSION → SourceVersion → HAS_CHUNK → Chunk.
Entity ← SUBJECT — Claim — OBJECT → Entity.
Claim → SUPPORTED_BY → Chunk.

- Document: 프로젝트 내 안정 ID, 출처 URI와 접근 등급. SourceVersion: 원문 내용 해시와 수집 시각. Chunk: 버전별 안정 ID, 원문 인용 위치(줄/페이지/대화 차례), 해시.
- Entity: 프로젝트/유형/고유 ID, 표시 이름, 별칭. 이름만으로 MERGE하지 않는다. 같은 이름의 다른 대상과 별칭을 구분하고, 불확실하면 병합 후보로 둔다.
- Claim: 주어·허용된 술어·목적어와 검토 상태, 근거, 추출 모델/지시문/스키마 판, 생성·검토 시각. 수치·날짜 같은 값은 유형이 정해진 값으로 모델링한다. 후보·승인·기각·낡음·철회 상태를 구분한다. 모순인 주장도 별도로 보존한다.
- 초기 의미 관계 사전은 제한한다(예: USES, DEPENDS_ON, DEFINES). 대상 프로젝트의 질문과 표본에서 조정한다. 기존 코드의 IMPLEMENTS/VERIFIES는 출처가 다른 관계임을 표시한다.
- 관계 이름을 무제한 생성하지 않는다. 공식 KG Builder의 스키마 지시만으로 검증을 대체할 수 없다. 허용 노드/술어/속성, 타입과 출처 연결을 저장 전에 별도로 검사한다.
- Neo4j Community에서 지원하는 복합 유일성 제약으로 ID 중복을 막고 필수값·참조 검사는 애플리케이션에서 한다. Enterprise 전용 제약을 MVP 전제로 두지 않는다.

## 수집·저장·갱신

1. 사용자가 선택한 자료만 등록하고 접근 등급을 확인한다. 원문을 불러와 버전별로 분할한다. PDF 지원은 텍스트 추출 품질을 별도 확인한 뒤 확장한다.
2. 호스트 작업자가 스키마에 따라 개체·관계 후보를 추출한다. 커널은 LLM을 호출하지 않고 원문·후보·승인 기록의 형식 검사와 저장을 맡는다. 기존 TypeScript·Neo4j 드라이버를 유지한다. 공식 Python GraphRAG SDK는 필요한 경우 별도 작업자 어댑터로 채택하고 실험적 KG API는 판을 고정한다.
3. 근거 문단과 관계 후보를 함께 보여주고 승인·수정·기각·개체 병합을 기록한다. 모델의 신뢰 점수만으로 자동 승인하지 않는다.
4. 승인·철회·병합 이벤트를 커널 저장 함수가 기록하고 Neo4j에 투영한다. 정확한 파일명/저장 경로는 구현 시 저장구조.md와 커널 계약을 함께 갱신한다. 이 계획에서 workspace 원문 파일을 손으로 만들지 않는다.
5. 의미 그래프는 기존 :Knowledge 전체교체 대상과 레이블/키를 분리한다. 원문과 승인 이력으로 재구축할 수 있어야 한다. 진짜 그래프 질의·탐색은 Neo4j에서 수행한다. DB 연결 실패는 명시하고 파일 검색을 같은 그래프 결과처럼 보여주지 않는다.
6. 수집은 프로젝트·자료 버전·스키마 판·작업 ID로 멱등 처리한다. 실패/취소 후 재시도와 부분 결과 복구를 검증한다. 자료 수정 시 과거 버전/검토를 보존하되 이전 근거 주장을 낡음으로 표시하고 기본 최신 질의에서 제외한다. 최신 원문에서도 같은 주장이 나오는지는 재검토한다.
7. 자료 제외·접근 권한 변경 때 검색/캐시/투영의 가시성도 갱신한다. 프로젝트와 접근 등급을 질의 시작부터 적용하고 결과를 받은 뒤에만 필터링하지 않는다.

## 질의·분석

- 1차는 개체 검색, 유형/관계 필터, 선택 노드의 1~2홉 확장, 두 개체 사이의 제한 경로, 근거 열기다. 승인 상태와 출처 버전을 함께 전달한다.
- Cypher는 매개변수화된 읽기 템플릿, 결과 수·홉 수·시간 제한을 사용한다. LLM이 만든 임의 Cypher나 DB 쓰기를 바로 실행하지 않는다.
- 2차 GraphRAG는 검색 질문→후보 문단/개체→Neo4j 관계 탐색→근거 수집→인용 답변이다. 일반 문서 검색과 비교하여 그래프가 필요한 질문에서 개선되는지 확인한다. 벡터 검색은 키워드/개체 기준선보다 유용함을 평가한 뒤 추가한다. 근거가 없는 답, 오래된 자료, 상충한 주장, 접근 불가를 구별한다.
- GDS는 승인된 의미 관계만 정의한 투영을 만든 뒤 stream 모드로 중심성·군집·유사도·경로를 실험한다. 전체 파일의 CONTAINS를 그대로 분석하지 않는다. 무엇을 노드/관계/방향/가중치로 썼는지와 데이터 범위를 함께 보여준다. 분석값은 검토된 사실과 별도이며 필요 시 가설로 검토한다.
- GraphQL은 외부 클라이언트/API 수요가 생길 때 추가한다. Bloom은 시각화 참고 사례이며 제품 내장 전제로 두지 않는다. APOC/GDS는 버전 호환·필요 프로시저·배포 조건을 확인한 뒤 별도 설치한다. 강의 주제를 모두 초기 필수 의존성으로 만들지 않는다.

## 순서와 완료 기준(제안 목표)

P0 질문·범위: 표본 자료 10개 내외, 질문 20개 내외, 사람이 정리한 관계/정답/근거 표본. 모순·동명이인·개정·답 없음·접근 제한 사례를 포함한다. 실제 시간/비용은 표본 추출 작업에서 측정한다.

P1 데이터 계약: 그래프 스키마·ID·버전·검토 상태·원문 위치·허용 관계, 샘플 Cypher, 저장 계약, 기존 그래프 격리. 두 번 수집해도 중복이 없고 자료 개정/재구축/접근 변경의 기대 결과가 같아야 한다.

P2 수집·검토 MVP: 문서 등록→후보 생성→근거 확인→승인→Neo4j 탐색. 1차 범위는 텍스트 문서와 사용자가 선택한 대화로 제한. 승인된 관계의 출처 추적 성공 100%, 기각/낡은 후보가 기본 질의에 섞이지 않는 사례 100%를 통과 기준으로 제안한다. 이는 실측 결과가 아니다.

P3 탐색·질문: 개체 검색과 경로, 근거 인용, 문서 개정 표시. GraphRAG는 별도 평가에서 채택 여부를 결정한다. 질문별 정답/근거 일치, 답 없음 처리, 인용 원문 일치, 지연시간·비용을 기록한다. 그래프 사용 유무를 비교한다.

P4 선택 확장: 충분히 검토된 데이터에서 GDS 1~2개 알고리즘을 시험하고 결과 해석을 검토한다. GraphQL·고급 자동화는 실제 수요가 있을 때 진행한다.

코드 실행·수정·추가 웹 조사 없이 이 문서의 가정과 근거를 비판적으로 검토해 달라. 특히 1) 사용자의 강의 적용 의도와의 정합성 2) 관계/근거/검토 상태 모델의 결함 3) 기존 전체교체 그래프에서의 이행 위험 4) MVP 범위 과다 5) Neo4j/GraphRAG/GDS의 기술적 부정확성 6) 단계별 통과 기준에서 빠진 사항을 우선순위와 구체적 수정안으로 적어 달라. 주장과 설계 제안을 구분하고, 자료를 직접 열람하지 못했다면 읽었다고 말하지 말라. 최종 화면 안 4가지는 이 검토를 반영한 다음 작성한다.
