# Claude 독립 검토 원문

제공한 계획만으로 검토했으며 코드 실행·수정·추가 자료 열람은 하지 않았습니다.

# Neo4j 지식 그래프 재설계 검토

**검토 전제:** 요청하신 대로 도구, 에이전트, 링크를 쓰지 않고 본문만 검토했습니다. 코드에 관한 사실은 문서에 적힌 내용을 그대로 전제로 했습니다. Neo4j 기능에 관한 언급은 제 기존 지식이므로 5.26에서 다시 확인해야 합니다.

## 높음: 반드시 수정

**1. 상태 3축의 위치가 잘못됨**
- **projectionStatus:** Neo4j 질의 필터로 쓸 수 없습니다. Neo4j에 있으면 이미 반영된 것이기 때문입니다.
  - 이 상태는 커널 이벤트 로그에만 둡니다.
  - Neo4j에는 alias별 `lastAppliedSeq` 커서를 같은 트랜잭션에서 갱신합니다.
  - UI는 커널의 seq와 비교해 "반영 대기 N건"을 표시합니다.
- **sourceStatus:** Claim이 아니라 근거(SUPPORTED_BY) 단위에 둡니다.
  - Claim의 현재성은 "approved + current 근거가 1개 이상"으로 파생 계산하고 따로 저장하지 않습니다. 이것으로 복수 근거 문제가 풀립니다.
  - 검토 상태도 근거별로 둡니다. 승인된 Claim에 재추출로 새 근거가 붙으면 그 근거만 pending입니다.
- **접근 불가:** `unavailable`에 섞지 마십시오. 권한은 보는 사람마다 달라서 저장 상태가 아니라 질의 시작 필터입니다. `unavailable`은 삭제나 제외에만 씁니다.

**2. 개정 시 stale 폭증**
- 문서 하나만 고쳐도 근거 전체가 stale이 되면 재검토 큐가 폭주합니다.
- 청크 해시가 같으면 근거를 새 버전으로 자동 이관하고, 이관 기록을 남깁니다.
- 변경된 청크의 근거만 stale로 표시합니다.
- 경계가 안정적이도록 제목·문단 기준으로 분할합니다.

**3. 투영 순서**
- eventId만으로는 순서가 보장되지 않습니다. 철회가 승인보다 먼저 반영될 수 있습니다.
- 수정안:
  - alias별 단조 증가 seq를 붙이고 순차 적용합니다.
  - 실패한 이벤트에서는 건너뛰지 않고 정지한 뒤 표시합니다.
  - 재구축은 seq 0부터 재생합니다.
  - 재구축 결과가 같은지 보는 동등성 테스트를 P1 기준에 넣습니다.

**4. 기존 그래프로의 이행 위험**
- 레이블 분리만으로는 부족합니다. 의미 노드와 `:Knowledge` 사이에 간선을 만들면 `replaceAlias`의 DETACH DELETE가 그 간선을 지웁니다.
- 교차 연결은 속성 참조(경로 + 해시)로 둡니다.
- "스캔을 실행해도 의미 그래프가 무손실"인지 확인하는 회귀 테스트를 추가합니다.

## 중간

5. **검색 중복:** 메모리 키워드 검색, CONTAINS 검색, 신규 개체 검색이 세 갈래가 됩니다. 검색 입구를 하나로 두고 결과 출처(스캔 / 의미 / 파일 대체)를 라벨로 구분하십시오. 의미 그래프 검색에는 CONTAINS 대신 전문 인덱스를 검토하십시오. Community에서도 지원된다고 알고 있으나 확인이 필요합니다.
6. **Claim 노드화의 비용:** 개체 사이 관계 하나가 2홉이 됩니다.
   - "1~2홉"과 제한 경로 정의를 Claim 경유 기준으로 다시 써야 합니다.
   - GDS는 Cypher 투영으로 Claim을 Entity→Entity 간선으로 접어서 투영하십시오.
7. **유일성 제약의 빈틈:** 유일성 제약은 속성의 존재를 강제하지 않으므로 id가 null인 레코드가 통과합니다. 앱 쪽 필수값 검사를 계약 테스트로 고정하십시오.
8. **기각 후보의 재등장:** 재수집하면 기각한 후보가 다시 나옵니다. 후보 지문(정규화한 주어·술어·목적어 + 청크 해시)으로 기각 이력과 대조하십시오.

## 범위 정합성

- 2~4번 지시와는 맞습니다.
- 다만 "문서 의미 그래프 중심"은 확인되지 않은 가정인데, 설계 전체가 이 가정에 달려 있습니다. 4안을 내기 전에 사용자에게 확인하십시오.
- "4안"을 DB 구조가 아닌 작업 흐름의 대안으로 재정의했다는 점도 명시해야 합니다.

## MVP 과다

P2에 대화 수집, 접근 등급, 개정 처리, 병합 후보, 템플릿 5개가 모두 들어 있습니다. 다음처럼 줄이기를 제안합니다.
- 자료는 텍스트·마크다운만 받습니다.
- 접근 등급 모델 대신 "제한 자료는 수집 금지"로 처리합니다.
- 술어는 3개로 제한합니다.
- 템플릿은 3개(개체 검색, 이웃, 주장 근거)만 둡니다.
- 경로, 개정 영향, 대화 수집은 P3로 옮깁니다.
- 평가 20문항은 유지하되, 미지원 유형은 "미지원이라고 정직하게 답하는지"로 채점합니다.

## 빠진 통과 기준

- 사람이 만든 표본 대비 관계 추출의 정밀도·재현율
- 문서당 후보 수, 검토 시간, 기각률 (P0에서 측정하고, 과다하면 술어를 줄임)
- 투영 지연의 상한과 실패 이벤트 복구
- 모든 템플릿에서 접근 누출 0건

## A~D 평가와 추천

- **A (문서→관계 후보→근거 검토):** 승인 데이터를 만드는 유일한 경로라서 선택지가 아니라 전제입니다. 주된 위험은 검토 피로입니다.
- **B (개체→관계 탐색→근거):** 승인 데이터가 쌓여야 가치가 생깁니다. 자료 10개 규모에서는 빈약할 수 있습니다.
- **C (질문→관계 검색→인용 답변):** 그래프를 쓸 때와 안 쓸 때를 비교 평가하기 전에는 기여를 입증할 수 없으므로 후속이 맞습니다.
- **D (범위→그래프 분석→해석):** 표본이 작아 중심성·군집의 의미가 약하고, 중요도로 오해될 위험이 큽니다. 마지막에 두십시오.

**추천:** A와 B를 대안으로 비교하지 말고, "A 중심 + B의 최소형"을 첫 화면으로 두십시오. B의 최소형은 이웃과 근거 열기만 있는 개체 상세 패널입니다. 비교 대상은 A 안의 검토 단위, 즉 청크별 검토와 문서별 일괄 검토로 바꾸기를 제안합니다.
