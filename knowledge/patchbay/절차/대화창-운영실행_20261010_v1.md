# 상담과 분리된 운영 대화 구현 · 2026-10-10

사용자 요청: 상담 전용 Plan과 운영 Act·Check·Deploy 아키텍처에 맞춰 대화창 구현. SQLite는 프로젝트 구현 완료 후 검증 단계에서 논의. 기존 Patchbay 사용 포트에서 반영.

## 구현

- 기존 `RoomPanel`의 일반 대화·토의를 유지하고 `RoomExecutionPanel`에 상담 채택본 참조, 리더·독립 검토자 선택, 실행 배정과 단계 띠를 추가했다.
- 승인본 version·digest·요구사항·완료 기준을 고정한다. 상담 채택 출처는 `ir.approved-provenance.json`으로 별도 스냅샷을 남겨 새 초안의 상담 출처와 섞이지 않게 했다. 이전 채택의 출처를 알 수 없으면 추정하지 않는다.
- 멤버 id를 유지하고 리더는 연결된 멤버와 승인된 요구사항만 배정한다. 복잡도·추천 강도·이유를 기록한다. 기본은 사용자 모델·강도 유지, 추천 적용은 사용자 선택이다. Claude와 Codex에 low/medium/high를 전달하며 지원하지 않는 공급자는 기본 설정을 사용한다.
- `roomWorkflowTemplate.ts`가 프로젝트의 기존 TypeScript LangGraph 환경에 운영 그래프를 생성·등록한다. 상태 전이와 체크포인트는 그 서버의 `interrupt`·`Command.resume`를 사용한다. 별도 DB나 자체 엔진을 추가하지 않았다. Python 전용 서버 설정과 사용자가 고친 파일은 덮지 않는다.
- 자동 시험 성공과 독립 검토의 통과·근거가 모두 있어야 적용 조건으로 넘어간다. 구현 오류는 Act 재시도, 요구 변경은 실행 대기와 기존 상담으로 연결한다. 상담 재검토 뒤 새 승인본을 채택해야 다시 시작한다.
- 시험·적용 명령은 사용자가 고른 실행 파일과 인자 배열을 shell 없이 실행한다. 적용은 명시한 대상의 사용자 확인을 기록한다. 배정 최대 8개, 모델/명령 3분, 수정 시도 최대 3회다.
- 운영 메시지·실행 근거는 `rooms/`, 그래프 연결은 `threads/`, 상담은 `consult/`에 분리한다. 완료된 operationId의 결과는 재사용한다. 시작만 기록된 작업은 중복 실행하지 않고 실제 상태 확인을 요구한다. JSONL은 프로세스 내 직렬화, 메타는 임시 파일 rename이다.
- MCP `get_room`은 원문을 증분 조회하며 상담은 기존 `consult_history`로 별도 조회한다. 조회가 그래프를 재개하지 않는다.
- PC·모바일은 같은 서버와 상대 경로 API를 사용한다. 원격 바인딩은 연결 토큰이 필요하며 조회·실행 토큰을 구분한다. 로그인은 HttpOnly/SameSite 쿠키로 유지한다.
- Discord/Telegram 알림은 채널 환경 설정과 실행별 사용자 선택이 있을 때만 상태·원문 링크를 전송한다. 결과를 기록하며 실패가 실행 결과를 바꾸지 않는다. 실제 메시지는 이번 작업에서 전송하지 않았다.

## 기존 포트와 사용 순서

실행 중이던 Patchbay는 **127.0.0.1:4318**이었다. CLI 기본 포트 4317과 구분한다. 새 API·화면은 기존 서버에 반영하며 별도 운영 포트를 만들지 않는다. 임시 화면 확인에 사용한 4328은 제품 설정에 포함하지 않는다. LangGraph는 기존 2024 연결을 유지한다.

1. 기존 Patchbay `http://127.0.0.1:4318`에서 프로젝트의 상담·PRD 검토·채택을 진행한다.
2. 대화창 LLM 화면에 수행 리더와 별도 검토자를 추가한다.
3. 「운영 실행 설정」에서 리더·검토자, 시험 명령 배열, 선택적 적용 명령·대상, 편집 허용 여부를 정한다.
4. 처음 연결하는 프로젝트에서는 「LangGraph 연결 준비」로 운영 그래프를 등록하고 프로젝트의 기존 그래프 서버를 다시 켠다. TypeScript LangGraph 의존성은 해당 프로젝트가 제공한다.
5. 「채택본으로 배정 요청」→추천·배정 확인→수행→검증을 진행한다. 적용 명령이 없으면 검증 완료로 종료할 수 있다.
6. 요구 변경은 상담으로 보낸다. 모바일에서는 운영 대화창을 닫고 상담 화면으로 이동한다.

원격 조회 설정: `PATCHBAY_FLOW_READ_TOKEN`(조회 전용), `PATCHBAY_FLOW_TOKEN`(조회·실행). 기존 포트 유지 예: `patchbay flow --port 4318 --host <연결 주소>`. 토큰은 URL이나 대화에 넣지 않는다.

알림 설정: `PATCHBAY_DISCORD_WEBHOOK`, `PATCHBAY_TELEGRAM_TOKEN`, `PATCHBAY_TELEGRAM_CHAT_ID`, 원문 접근 주소 `PATCHBAY_PUBLIC_URL`. 설정 자체로는 전송하지 않으며 해당 실행의 알림 선택이 필요하다.

## 확인 결과

- 기존 4318 서버를 갱신하고 임시 4328 서버 종료를 확인했다. 실제 서버의 세션 조회 200, 새 실행 API의 빈 요청 400을 확인했다. Patchbay 자체 프로젝트에는 아직 채택본이 없어 승인본 조회는 정상적으로 409를 반환한다. 운영 실행은 프로젝트 상담에서 채택본을 만든 뒤 시작한다. 현재 메신저 채널은 미설정이다.

- 전체 시험 **119개 파일·1,045개 통과**. 명령: `CHOKIDAR_USEPOLLING=1 node node_modules/vitest/vitest.mjs run --maxWorkers=2 --reporter=dot` (`dev/`). 네이티브 파일 감시가 이 환경에서 EMFILE을 내므로 시험에서는 폴링을 사용했다.
- Core/CLI/MCP TypeScript 빌드, Flow 타입 검사·서버 빌드, Vite 클라이언트 빌드 통과. 기존 브라우저 번들의 node 모듈 외부화/크기 경고는 남아 있다.
- 기존 외부 프로젝트에 설치된 LangGraph 1.4.15를 읽기 전용으로 사용하고 임시 파일에서 실제 노드·interrupt·Command.resume·시험 실패 Act 복귀·대상 확인·완료 체크포인트를 확인했다. 시험용 메모리 체크포인터이며 DB 도입이 아니다.
- 임시 예시 자료를 Chrome에서 PC와 390px 모바일로 렌더링했다. 자바스크립트 예외 없음, 모바일 문서 너비 390px로 가로 넘침 없음. [PC 화면](대화창-운영실행_20261010_v1/desktop.png), [모바일 화면](대화창-운영실행_20261010_v1/mobile.png). 화면의 모델·배정은 가상 확인 사례다.
- 실제 공급자 응답 품질·사용자 앱 계정의 MCP 연결·휴대폰 실기기·배포·메신저 전송은 별도 실물 검증으로 남긴다. 상담 품질 평가·자동 개선 시스템도 별도 작업이다. 이번 확인에서 사용자 프로젝트의 그래프 설정·코드를 변경하지 않았다.
- SQLite는 설치하지 않았다. `package.json`·잠금 파일에 새 DB 의존성이 없으며 이후 검증 단계에서 논의한다.
