## 테스트에서 잡은 구멍

실패 자료 26건 중 **넷은 스키마가 먼저 막는다** — `done: []`(min 1) · `cap:admin`(enum) ·
`pattern: 기타`(enum) · 잘못된 reducer(enum). 처음 쓴 테스트는 그때 이렇게 했다:

```ts
const parsed = parseIr(mutated);
if (!parsed.ok) return;        // ← 그 검사 넷은 영영 안 돈다. 그래도 초록이다.
```

**고정 자료를 만든 이유가 바로 이것인데 테스트가 같은 함정에 빠졌다.** 지금은 두 층을 다 본다:

```ts
const ir = parsed.ok ? parsed.ir : (mutated as Ir);
expect(summary.failed).toContain(checkId);
```

그리고 「스키마도 막고, DRC도 같은 칸을 지목한다」를 따로 시험한다. 둘 다 필요한 이유는
**M4 생성기처럼 `parseIr`를 거치지 않고 IR을 만드는 길**이 있어서다.

## 설계 판단 둘

**1. CLI가 YAML을 직접 읽지 않는다.** 처음엔 `yaml`을 CLI에 넣으려 했는데, 스튜디오 파일 I/O는
Core의 몫이다(원칙 8 — CLI·MCP·React가 같은 Core 타입을 본다). `core/src/studio/irStore.ts`가
읽고, 아무것도 쓰지 않는다 — `overlay.ir`의 쓰기 경로는 `ir adopt` 하나여야 하고,
읽으면서 쓸 수도 있는 도구는 관문을 선택 사항으로 만든다.

**2. `--file`의 문서 루트는 그 파일 옆이다.** 처음엔 프로젝트 레포로 잡았더니 고정 자료를
검사할 때 `1.6/doc-exists`가 늘 깨졌다 — 그 IR의 문서는 레포가 아니라 자기 옆에 있다.
`--docs`로 바꿀 수 있게 두었다.

## 스키마와 DRC의 경계

| 층 | 무엇을 본다 | 왜 |
| --- | --- | --- |
| 스키마 (`irSchema`) | **모양** — 필드·타입·값 영역 | 빈 배열을 거절하지 않는다. 초안을 쓰기 시작한 순간 거절하면 아무도 안 쓴다 |
| DRC (`runIrChecks`) | **설계 규칙** — 도달성·추적 표·권한 | 실패를 **칸**으로 말한다. 스키마 오류는 「어디로 돌아가나」에 답하지 못한다 |

`done`의 「1개 이상」만 스키마에 두었다 — 완료 조건이 없는 IR은 모양부터 IR이 아니다.

## 남은 것

`ir adopt`는 **아직 없다.** 명세 §2.3이 정한 유일한 쓰기 경로이고, 차이 보기(`ir diff`)까지
왔으니 다음은 채택이다. 다만 M3(확인 화면)이 「사람이 화면에서 칸을 통과시킨다」이므로,
**채택 버튼이 화면에 붙는 것이 자연스럽다** — M3에서 같이 한다.
