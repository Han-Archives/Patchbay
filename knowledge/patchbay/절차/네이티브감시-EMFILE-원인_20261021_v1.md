# 네이티브 파일 감시 EMFILE — 원인 조사

## 결론

코드나 자원 누수 문제가 아니다. **Codex를 `--sandbox workspace-write`(macOS seatbelt)로 띄운 환경에서만** 나는 실패다.

## 근거

1. **실패한 실행은 모두 Codex 차례였다.** 대화 기록에서 EMFILE 실패 보고는 6번 나왔고 모두 Codex 차례다(`2026-10-13-fd555bdc` 16·20줄, `2026-10-17-3a421920` 4·16줄, `2026-10-20-bebb32c3` 11줄, `2026-10-21-867166bc`). Claude가 전체 시험을 돌린 유일한 차례(`2026-10-17-3a421920` 20줄, 2026-10-20)는 504건 통과에 EMFILE이 없었다.
2. **같은 Codex 차례에 샌드박스 증상이 같이 나왔다.** `Operation not permitted`(내부 앱 서버 시작), `~/.patchbay` 쓰기 `EPERM`. Patchbay는 Codex를 `exec --sandbox workspace-write|read-only`로 띄운다(`app/apps/flow/src/roomHost.ts:105`).
3. **실패하는 4건은 디렉터리를 네이티브로 감시하는 시험뿐이다.** `studioWatch.test.ts` 3건과 `server.test.ts`의 `watch: true` SSE 1건이다. 감시 대상은 임시 폴더의 파일 몇 개뿐이라 열린 파일 수 한도를 넘을 규모가 아니다.
4. **폴링으로 바꾸면 모두 통과한다.** `CHOKIDAR_USEPOLLING=1`에서는 47건 모두 통과했다(Codex, 2026-10-21). 재기동해도 그대로였다.
5. **동작 경로.** chokidar 5는 macOS에서 `fs.watch`를 쓰고(`handler.js:126`), Node(libuv)는 디렉터리 감시에 FSEvents를 쓴다. libuv는 `FSEventStreamStart`가 실패하면 `UV_EMFILE`을 돌려준다. seatbelt 샌드박스가 FSEvents 서비스 접근을 막으면 파일 수와 상관없이 「too many open files, watch」가 뜬다.

## 남은 불확실성

- 이번 차례에는 셸 실행 권한이 없어서 같은 시험을 샌드박스 밖에서 직접 재현하지 못했다. 1번 근거는 2026-10-20 기록 하나에 기댄다.
- Codex seatbelt 정책이 FSEvents mach 서비스를 막는다는 것은 정책 원문으로 확인하지 않았다. 증상과 libuv 동작에서 끌어낸 추론이다.

## 정할 것 (사람)

- A. 코드는 고치지 않는다. Codex 차례의 전체 시험 기준을 `CHOKIDAR_USEPOLLING=1`로 정하고, 네이티브 감시 4건은 샌드박스 밖(Claude 차례나 사람)에서 확인한다.
- B. A에 더해, 샌드박스에서 이 4건을 건너뛰고 이유를 표시하는 시험 조건을 넣는다. 「실패 4건」이 매번 보고되는 일은 사라지지만 시험 코드를 고쳐야 한다.
- 권장: A. 제품 동작은 정상이고, 시험이 실제 네이티브 감시를 검증하는 가치가 남는다.
