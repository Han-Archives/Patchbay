읽기만 수행했으며 파일은 변경하지 않았습니다. 현재 기획은 **기록된 사건을 모아 보는 기능**과 **실제로 일어난 모든 변동을 보존하는 기능**을 혼용합니다. 특히 원문이 사라진 뒤에도 과거 기록을 만들 수 있다는 가정부터 수정해야 합니다.

아래 `기획:줄`은 [검토 대상 문서](../Log-일일기록-기획_20261015_v1.md)를 뜻합니다. 코드 경로는 레포 기준입니다.

### A. R1~R5 충족 여부

- **[심각도 높음] R1 — 부분 충족.** 날짜별 Markdown과 조회 버튼은 있지만, “일일 변동사항”의 범위가 불명확합니다. 현재 수집안은 추가·완료 중심이며 삭제·수정·재정렬을 복원할 수 없습니다. 화면을 열지 않는 동안 생성됐다 사라진 항목은 기록되지 않습니다. **근거:** 기획:21–30, 157–166; `app/packages/core/src/studio/todoStore.ts:103–117`, `cycleItemStore.ts:49–59`. **제안:** v1의 보장을 “원문에 남아 있는 사건의 날짜별 집계”로 명시하십시오. 삭제까지 보장하려면 해당 변경 명령에서 최소 사건 기록을 남기는 방식이 필요합니다.

- **[심각도 중간] R2 — 기능 계획은 있으나 근거가 부족합니다.** 사용자 발언 앞부분만 받은 모델은 실제 결과·결정·막힘을 알 수 없습니다. 앞 120자는 요약도 아닙니다. **근거:** 기획:119, 200–201. **제안:** “사용자 발언 발췌”로 이름을 바꾸고, 요약에 사용할 결과는 `did`·완료 기록·명시적으로 선택한 답변 등으로 한정하십시오. 근거가 없으면 “확인되지 않음”을 출력해야 합니다.

- **[심각도 높음] R3 — 부분 충족.** 색인 표는 제안했지만 “어떤 항목이 주로 변경됐는가”를 태그 빈도로 대체했습니다. 사건 수·파일 수·대화방 수가 섞이면 주로 바뀐 대상을 판단하기 어렵습니다. **근거:** 기획:86–93, 129–137, 224–226. **제안:** 사건에 `대상 종류 + 대상 ID + 변경 종류`를 두고, 태그별 **사건 수**와 **고유 파일 수**를 분리하십시오. 대화는 방 전체보다 날짜별 발언 묶음으로 색인하십시오.

- **[심각도 중간] R4 — 부분 충족, 요구보다 범위가 큽니다.** 사용자는 보고서의 바탕 문서를 요구했는데 보고서 생성·판 관리까지 포함했습니다. 반면 요약 없는 날에 `did`도 없으면 보고서 재료가 비게 됩니다. **근거:** 기획:15, 206, 237; `app/packages/core/src/types/progress.ts:20–22`. **제안:** v1은 기간별 근거 모음과 Markdown 내보내기로 충분합니다. 보고서를 생성한다면 `did → summary → 다른 사건 목록` 순의 대체 규칙과 수집 누락 표시를 정하십시오.

- **[심각도 중간] R5 — 경로 설계만 충족했습니다.** alias별 폴더는 제안했지만 API·CLI·MCP의 등록 확인, 프로젝트 간 격리, 캐시 키 검증이 완료 기준에 없습니다. **근거:** 기획:16, 258–263; `app/packages/core/src/studio/studioStore.ts:156–157`은 단순 경로 결합입니다. **제안:** 모든 진입점에서 등록된 alias를 확인하고 날짜·보고서 이름의 경로 이탈을 막으십시오. 두 프로젝트에 같은 날짜·room ID가 있는 시험을 넣어야 합니다.

### B. 실제 코드와 어긋나는 가정

- **[심각도 높음] 할일의 `at`은 생성 시각으로 사용되지만 전체 변경 이력은 아닙니다.** Flow 추가·동기화는 `now.toISOString()`을 넣습니다. 완료 시각은 저장 함수가 설정하지만 미완료로 되돌리면 제거합니다. 완료 보관 색인은 별도로 남으므로 현재 목록과 보관 목록을 합치면 중복이나 상태 충돌도 생깁니다. 삭제 시각·수정 시각 필드는 없습니다. **근거:** `app/apps/flow/src/todoActions.ts:33–41`; `app/packages/core/src/studio/todoStore.ts:16–27, 93–97, 108–117`. **제안:** 추가와 완료를 서로 다른 사건 ID로 만들고 현재/보관을 todo ID로 중복 제거하십시오. 반복 완료 이력과 삭제는 현재 자료로 복원 불가라고 명시하십시오.

- **[심각도 높음] 방 메시지 `at`은 미러 원문의 발언 시각이 아닙니다.** 저장 함수는 항상 전달받은 `now`로 `at`을 만듭니다. 미러는 원문 timestamp를 읽더라도 메시지 저장에는 `now()`를 전달합니다. 늦게 바인딩하거나 재시도하면 과거 대화가 오늘 대화로 잡힙니다. **근거:** `app/packages/core/src/rooms/store.ts:104–118`; `mirror.ts:203–223, 235–246`. **제안:** 현재는 “방 기록 시각 기준”이라고 표시하십시오. 원래 날짜로 묶으려면 `sourceAt`과 `recordedAt`을 구분하는 원문 계약 변경이 먼저입니다.

- **[심각도 중간] 방 메타데이터는 과거 상태 기록이 아닙니다.** 제목·멤버·현재 모드는 변경 가능한 최신 값입니다. 미러 메시지는 사용자 말·답·모델을 옮기지만 당시 모드 필드는 넣지 않습니다. **근거:** `app/packages/core/src/rooms/store.ts:275–305`; `mirror.ts:207–223`; `types.ts:58–62`. **제안:** 제목은 “현재 제목”, 모드는 메시지에 실제 저장된 경우만 표시하십시오. 현재 메타데이터를 과거 대화의 상태로 해석하면 안 됩니다.

- **[심각도 중간] 흐름도 태그 상속은 조인이 필요합니다.** 태그는 cycle item의 단일 `tag`이고 할일에는 태그 필드가 없습니다. 연결은 cycle item의 `todoId`, 할일의 `roomId`입니다. progress에는 이 연결이 없습니다. **근거:** `app/packages/core/src/studio/cycleItemStore.ts:15–26`; `todoStore.ts:16–27`; `app/packages/core/src/types/progress.ts:16–24`. **제안:** `cycleItem → todo → room`의 명시적 연결에서만 상속하십시오. 여러 항목이 한 할일에 연결될 때의 합집합 규칙도 정해야 합니다.

- **[심각도 높음] git의 미커밋 변경은 “오늘 변경”이 아닙니다.** 이 환경에서 git 실행과 현재 Patchbay 레포는 확인했습니다. 그러나 기존 `gitDirtySnapshot`도 git 저장소가 아니면 `null`을 허용합니다. 현재 dirty 상태에는 며칠 전 변경도 포함되며, 파일 수정 시각으로 ±30분의 사건 관계를 증명할 수 없습니다. **근거:** 기획:30, 109–113, 153; `app/apps/flow/src/roomHost.ts:300–304`. **제안:** 커밋은 선택한 커밋 시각 기준 사건, 미커밋 파일은 “조회 시점 작업 트리 상태”라는 별도 스냅샷으로 표시하십시오. 비git·HEAD 없음·경로 없음은 오류 대신 수집 불가 상태로 남기십시오.

- **[심각도 중간] 등록부 `path`와 작업 공간 경로는 서로 다릅니다.** `path`는 프로젝트 레포 루트이고 Log 저장 위치는 `projectStudioDir(home, alias)`입니다. `workspace/`는 실제 배치 예시이며 코드에서 고정하면 안 됩니다. **근거:** `app/packages/core/src/types/studio.ts:12–21`; `studio/studioStore.ts:156–157`; `knowledge/patchbay/규칙/storage-layout.mdc:32–36`. **제안:** git 읽기는 등록부 `path`, Log 저장은 해석된 `PATCHBAY_HOME`으로 구분하십시오. `docs`도 Log 저장 위치로 사용하지 마십시오.

- **[심각도 중간] progress는 작업 발생 시각이 아니라 보고 시각입니다.** `timestamp`는 쓰기 시점이고 `asked`·`did`는 선택 사항입니다. 화면의 기존 동작을 설명한 부분은 실제 코드와 맞지만, 이를 완전한 활동 이력으로 확대하면 안 됩니다. **근거:** `app/packages/core/src/studio/progressStore.ts:95–106`; `app/apps/flow/src/dashboardView.ts:176–178`; `ProjectLogPane.tsx:12–20`. **제안:** “진행 보고가 기록된 날”로 정의하고 제목은 `step → summary`, 결과는 `did → summary` 순으로 처리하십시오.

- **[심각도 중간] LM Studio 호출 재사용과 모델 자동 선택은 별개입니다.** 기존 경로는 `lms chat -p … --system-prompt … <model>`이며 빈 local 모델 ID를 거절합니다. “로딩된 첫 모델” 선택은 기존 동작이 아닙니다. 기획에 적힌 설치·로딩 모델 목록도 이번 정적 코드 검토로 확인된 사실은 아닙니다. **근거:** 기획:32, 199; `app/apps/flow/src/roomHost.ts:114–115, 395–400`. **제안:** 모델 ID를 명시적으로 선택·저장하고 실행 시 가용성을 확인하십시오. 고정 모델명을 구현 전제로 삼지 마십시오.

### C. 설계 위험

- **[심각도 높음] 마감된 일일 기록은 더 이상 순수 파생물이 아닙니다.** 원문 삭제 뒤에도 보존하는 날짜별 문서는 스냅샷입니다. 그런데 색인은 “언제든 다시 생성”한다고 하므로 원문에서 재생성하면 마감 문서와 달라집니다. **근거:** 기획:61, 69–71, 166. **제안:** 마감 스냅샷에 정규화된 사건과 출처 정보를 함께 보존하고 색인은 그 자료에서 재생성하십시오. 그렇지 않으면 “원문만으로 재생성 가능” 보장을 철회해야 합니다.

- **[심각도 높음] 첫 사후 생성은 유실을 막지 못합니다.** 지난주에 생성·삭제된 할일은 오늘 처음 정리해도 복원되지 않습니다. 미러 도착이 늦으면 잘못된 날짜를 마감할 수도 있습니다. **근거:** 기획:161–166; `app/packages/core/src/studio/todoStore.ts:108–117`; `rooms/mirror.ts:223`. **제안:** 마감은 사용자 확정 또는 변경 가능한 잠정 스냅샷으로 시작하십시오. 확정 시 수집 범위·누락·기준 시각을 저장하고, 늦은 자료는 정정본으로 연결하십시오.

- **[심각도 높음] 생성 계기와 제공 인터페이스가 일치하지 않습니다.** 표에는 MCP `log_build`가 있지만 L6에는 `log_read`만 있습니다. 보고서 생성 전에 해당 기간을 정리한다는 규칙도 없습니다. **근거:** 기획:161–164, 261–263. **제안:** 공통 build 서비스를 두고 화면·CLI·MCP·보고서가 동일하게 호출하도록 명세하십시오. 화면 조회는 읽기와 생성 요청을 구분하고, 생성 시 수집 기준 시각과 부분 실패를 반환하십시오.

- **[심각도 높음] 태그의 ‘확정’ 표시와 ±30분 추정이 오해를 만듭니다.** 낱말 일치는 분류 규칙의 결과일 뿐 실제 변경 영역의 확정 증거가 아닙니다. 동시에 진행한 업무, 오래된 dirty 파일, 지연된 미러가 근처 변경 오탐을 만듭니다. **근거:** 기획:147–153. **제안:** v1에서 근처 변경은 제외하십시오. 연결·경로·낱말·LLM의 출처를 구분하고, 추정 태그는 기본 집계에서 빼십시오. LLM 제안 한 번 채택이 전역 낱말 규칙 추가로 이어지지 않도록 하십시오.

- **[심각도 높음] 사건 ID와 요약 입력이 연결되지 않습니다.** 요약은 일일 기록 본문만 받는데 Markdown 예시에는 사건 ID가 없습니다. 방 ID만 사용하는 색인은 여러 날짜에 걸친 방을 충돌시키고, progress timestamp만으로는 고유성을 보장하지 못합니다. **근거:** 기획:95–116, 129–135, 200–201; `rooms/store.ts:116–117`은 seq를 0부터 생성합니다. **제안:** Markdown에도 안정적인 사건 ID를 넣으십시오. 대화 ID는 날짜와 room ID를 포함하고 실제 seq 범위를 사용해야 합니다. 요약의 모든 근거 ID가 입력에 존재하는지 검사하십시오.

- **[심각도 중간] 하루 경계와 결정성 기준이 충돌합니다.** 실행 때마다 달라지는 `built`·`builtAt`을 포함하면 같은 원문으로 바이트가 같을 수 없습니다. 시간대·태그 설정이 바뀌어도 결과가 달라집니다. 방 ID 날짜도 UTC로 생성됩니다. **근거:** 기획:61, 84, 127, 166, 258; `rooms/store.ts:62–63`. **제안:** 결정성 입력을 원문·설정·생성기 버전으로 정의하고 실행 시각은 별도 관리하십시오. 날짜는 room ID가 아닌 timestamp로 계산하고 `[당일 자정, 다음 날 자정)`을 사용하십시오. 시간대 변경·DST·잘못된 시각 처리도 정해야 합니다.

- **[심각도 높음] rename만으로 동시 쓰기를 해결할 수 없습니다.** Flow·CLI·MCP가 동시에 전체 색인을 갱신하면 마지막 쓰기가 다른 날짜의 변경을 지웁니다. 보고서의 “없으면 생성”도 확인과 쓰기 사이에 경쟁이 있습니다. **근거:** 기획:69–73, 258–263; 기존 프로세스 간 잠금 사례는 `rooms/store.ts:30–58`. **제안:** 프로젝트별 프로세스 간 build 잠금, 세대 번호와 복구 규칙을 두십시오. 보고서는 배타적 생성으로 보호하고, 요약 완료 직전 원본 해시를 다시 확인해야 합니다.

- **[심각도 중간] 전체 색인·전체 원문 읽기의 크기 제한이 없습니다.** 방당 발췌 제한은 출력만 줄이며 방 JSONL 전체 읽기 비용은 줄이지 않습니다. 전 기간 `index.json`의 반복 재작성과 수백 ms 보장도 근거가 없습니다. **근거:** 기획:119, 161, 200; `rooms/store.ts:81–101`. **제안:** 초기 범위·최대 읽기량·페이지 크기를 정하고 큰 자료는 명시적 과거 생성으로 처리하십시오. “빈 날”, “미수집”, “수집 실패”를 구분해야 합니다. 성능 측정 후 색인 분할 여부를 결정하십시오.

- **[심각도 높음] 접근 등급 한 줄은 접근 제어 구현이 아닙니다.** `access.yaml`은 현재 기록용이며 첫 일치 규칙을 사용합니다. 새 허가 규칙을 일반 `workspace/**` 뒤에 넣으면 적용되지 않습니다. 대화 발췌·색인 제목·요약·보고서·보관본·내려받기 모두 민감 정보를 복제합니다. **근거:** `access.yaml:4–8, 39–41`; 기획:75, 192. **제안:** 허가 규칙을 포괄 규칙 앞에 두고 API·MCP에서 실제 접근 범위를 정의하십시오. 비밀정보 제외, 원문 삭제 후 파생 사본 처리, 백업 잔존 정책도 필요합니다. 다른 `PATCHBAY_HOME` 배치에서 경로 판정이 어떻게 되는지도 명시해야 합니다.

- **[심각도 높음] 로컬 모델도 실패·환각·입력 내 지시문 문제를 가집니다.** 12,000자 분할은 토큰 한도 보장이 아니고, 근거 ID가 존재해도 문장을 뒷받침한다는 보장은 없습니다. 낡은 요약을 보고서에 가져오는 제한도 없습니다. **근거:** 기획:199–206. **제안:** 자료를 명령이 아닌 인용 데이터로 구분하고, 토큰 예산·청크별 근거 보존·시간 초과·취소·출력 검증을 정하십시오. 실패하면 기존 요약을 유지하고, 낡거나 검증 실패한 요약은 기본 보고서에서 제외하십시오. 모델·프롬프트 버전·입력 해시를 저장하고 LLM 작성 문장임을 보고서에도 남기십시오.

### D. 더 단순하게 할 곳

- **[심각도 중간] v1 태그를 명시적 연결·경로·낱말 세 가지로 줄이십시오.** 근처 변경과 LLM 제안의 전역 규칙화는 별도 기능입니다. **근거:** 기획:145–153, 259, 262. **제안:** 분류되지 않은 사건을 허용하고 오탐을 먼저 측정하십시오.

- **[심각도 낮음] 열지도·태그 막대·기간 비교를 모두 첫 단계에 넣을 필요는 없습니다.** `visual-first`는 이 세 시각화를 의무화하지 않습니다. **근거:** 기획:170–189, 224–226; `knowledge/patchbay/규칙/visual-first.mdc:8–12`. **제안:** 날짜 선택 패널·태그 분포·요구된 색인 표로 시작하고, 지난 기간 대비와 복합 필터 연동은 뒤로 미루십시오.

- **[심각도 중간] 자동 보고서 판 관리보다 기간별 근거 내보내기를 먼저 만드십시오.** `-b`, `-c`는 최신 파일 판별과 저작물 보호 문제를 추가합니다. **근거:** 기획:192, 237; `knowledge/patchbay/규칙/doc-versions.mdc:8–26, 54–58`. **제안:** 초기에는 기존 보고서 열기와 새 이름으로 내보내기만 제공하십시오. 보고서를 독립 기록으로 볼지 같은 문서의 새 판으로 볼지 정하고, Log 보관 경로의 규칙 예외도 명시하십시오. 이번 절차 문서의 `_v1` 자체는 규칙상 문제가 아닙니다.

### E. D1~D5 의견

- **[심각도 높음] D1 — 현재 추천에 반대합니다.** “다음 날 처음 정리 때 고정”은 완전성을 확인하지 않은 자료를 확정합니다. **근거:** 기획:166, 244; `rooms/mirror.ts:207–223`. **제안:** v1은 잠정 기록과 명시적 확정으로 시작하십시오. 자동 마감은 원문 보존·지연 도착·정정 규칙이 마련된 뒤 도입해야 합니다.

- **[심각도 중간] D2 — 조건부 동의합니다.** 사용자 발언 발췌와 방 링크는 조회에는 쓸 수 있지만 결정·성과 요약의 충분한 근거는 아닙니다. **근거:** 기획:119, 201, 245. **제안:** 발췌임을 표시하고 결과 근거는 `did`나 선택된 답변을 별도로 연결하십시오. 10개 제한으로 생략한 발언 수도 표시해야 합니다.

- **[심각도 중간] D3 — LM Studio 재사용에는 동의, 고정 모델 추천에는 반대합니다.** 호출 경로는 있지만 모델 자동 선택은 추가 구현입니다. **근거:** 기획:199, 246; `roomHost.ts:114–115, 399–400`. **제안:** 사용자가 선택한 로컬 대화 모델 ID를 저장하고 가용성과 입력 한도를 확인하십시오.

- **[심각도 중간] D4 — 조건부 동의합니다.** 작업 공간 보관은 맞지만 `reports/`는 사람 편집을 허용하는 저작물 영역이라는 예외가 필요합니다. **근거:** 기획:73, 192, 247; `knowledge/patchbay/규칙/storage-layout.mdc:23, 50`. **제안:** 저장구조에 편집 주체와 덮어쓰기 금지를 명시하고, 백업 명령이 있다는 사실과 실제 백업 완료 상태를 구분하십시오.

- **[심각도 낮음] D5 — 동의합니다.** 명시적 바인딩 범위로 제한하는 편이 프로젝트 혼입을 줄입니다. 다만 바인딩된 대화도 완전한 원문 복제는 아닙니다. **근거:** 기획:248; `rooms/mirror.ts:19, 76–98, 196–197`. **제안:** 미바인딩·필터링·길이 제한·미러 지연으로 빠질 수 있는 범위를 화면에 설명하십시오. 238줄의 “문장 다듬기—D5 참고”는 잘못된 참조이므로 제거해야 합니다.

### F. L1~L6 순서·완료 기준 수정

권장 순서는 **L1 계약·수집 → L2 분류 → L3 조회 → L4 보고서 근거 → L5 요약 → L6 MCP**입니다. 순서보다 L1에 빠진 선행 계약과 각 단계의 검증 범위를 고치는 일이 우선입니다.

- **[심각도 높음] L1 — 마감 구현 전에 사건 계약과 보존 방식을 확정하십시오.** **근거:** 기획:258; `todoStore.ts:108–117`; `rooms/mirror.ts:223`. **제안/완료 기준:** 사건 ID·기록 시각·출처 시각·시간대·중복 제거·수집 불가 상태를 먼저 정의하십시오. 재실행 동일성, 현재/보관 중복, 지연 미러, 삭제된 원문, 손상 JSONL, 비git, 동시 실행·중단 복구를 고정자료로 검증해야 합니다.

- **[심각도 중간] L2 — 근처 변경을 제외하고 집계 단위를 확정하십시오.** **근거:** 기획:259, 152. **제안/완료 기준:** 연결 상속·경로·낱말의 중첩과 우선순위, 미분류, 사용자 추가 태그를 검증하십시오. “규칙 밖 태그 거절”은 프로젝트가 태그를 더할 수 있다는 계약과 맞춰 정의해야 합니다.

- **[심각도 높음] L3 — 화면 표시뿐 아니라 격리·부분 실패·출처 이동을 검증하십시오.** **근거:** 기획:190, 260; `rooms/store.ts:75–101`. **제안/완료 기준:** 프로젝트 전환 중 응답 경합, 미수집/빈 날/실패 구분, 삭제된 출처, 실제 seq 이동, Markdown 안전 렌더링, 접근 등급 적용을 포함하십시오. 문서 갱신도 이 단계까지 미루지 말고 경로·API가 도입되는 단계에 함께 하십시오.

- **[심각도 중간] L4 — LLM 없이도 완성되는 보고서 근거를 만드십시오.** **근거:** 기획:206, 261. **제안/완료 기준:** 기간 정리 후 생성, `did` 없는 날의 대체, 진행 중인 기간 표시, 주·월·연도 경계, 기존 파일 보호와 동시 생성을 검증하십시오. 처음에는 요약 없이 동작하고 L5에서 검증된 요약만 연결하십시오.

- **[심각도 높음] L5 — 성공 외의 상태를 완료 기준에 넣으십시오.** **근거:** 기획:200–202, 262; `roomHost.ts:275–283`. **제안/완료 기준:** 모델 없음·실행 중 모델 해제·시간 초과·취소·빈 출력·형식 오류·가짜 근거 ID·생성 중 원문 변경·긴 입력을 검증하십시오. 실패 시 이전 요약 보존과 태그 설정의 무변경을 확인해야 합니다.

- **[심각도 중간] L6 — MCP 기능 목록부터 일치시키십시오.** 읽기 도구만으로는 “오늘 기록 정리”를 제공하지 못합니다. **근거:** 기획:162, 263. **제안/완료 기준:** `log_read`와 `log_build`를 명세에 일치시키고, 보고서 생성 도구의 필요 여부도 결정하십시오. 기간·태그 제한, 응답 크기, 페이지 처리, 프로젝트 격리와 허가 범위를 검증하십시오.
